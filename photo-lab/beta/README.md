## What is implemented

- `src/photo/http-gateway.ts`: bounded single-JPEG HTTP client compatible with the existing photo UI. No Supabase SDK/key in the browser, no direct bucket URLs, credentials omitted, redirects rejected and responses bounded/validated. `beta-entry.ts` is disabled and **not imported by the ordinary app**. Selected list IDs are not embedded in public JavaScript.
- `handler.ts` and `engine.ts`: anonymous link-scoped actions (`get`, `put`, `status`, `remove`, `delete`) over one POST endpoint, strict query/method/body limits, approved browser origins, sanitized errors and no-store responses. No-origin callers work deliberately: CORS is not authorization. There is no private ownership or per-person revocation claim.
- `text-authority.ts`: checks the exact selected list's existing public `v2/listClaims/<list>` value and exact `v2/lists/<list>/<item>` text record through pinned, read-only Firebase REST paths. The claim must be `true`; the item must have valid nonblank text, ID and boolean checked fields. Input IDs are validated and encoded; client claims, arbitrary paths, parent listing and alternate databases are not accepted. Missing/malformed/outage responses fail closed. Item text is discarded, never stored in photo metadata. No photo bytes, associations, counters or processing go through Firebase or Netlify.
- `ledger.ts` and the disabled migration: a finite server-owned ledger in a private PostgreSQL schema. A global compare-and-swap revision serializes independent workers. The SQL function locks the existing trial global budget first, then the beta row; a digest of the current legacy row and exact control settings prevents stale updates. SQL independently checks combined byte/count caps and prevents deletion of history or counter rollback. No trial row is updated. Installation requires the exact accepted, quiescent trial counters, blocked original batch, complete continuation and unchanged expiry; drift stops the migration. RLS is enabled, public RPC execute revoked, and only the existing service role can use the invoker RPCs; that role cannot change the control column. No SECURITY DEFINER or client table/Storage policy is introduced.
- `sdk.ts`: the existing pinned official server client accesses a separate private bucket. Bucket configuration must match; there is no automatic bucket creation. Keys derive only from operation UUIDs, uploads use `upsert:false`, and only exact `NoSuchKey` responses prove absence. Reuses the unchanged codec from the accepted trial; output is independently encoded and bounded.
- `cleanup-journal.ts`: per-item device-local retry intent in a separate namespace, containing only item IDs and a marker. Authoritative photo metadata/accounting stays in the backend. Different tabs cannot overwrite one another's item markers. A maximum of 100 markers is checked; browser storage failure is reported and text deletion still succeeds. The marker is removed only after server cleanup succeeds. It is not a photo backup or a durable service ledger.

The browser normalizes first: baseline JPEG ≤512 KiB and ≤1280 pixels, orientation applied and metadata stripped. The server independently validates/reencodes full ≤384 KiB and thumbnail ≤32 KiB/192 pixels. Client-supplied hashes/thumbnails are never trusted. A valid normalized input can still be rejected at the server output cap. The previous JPEG/HEIC fallback remains; actual iPhone/Android camera behavior is untested.

## Link access and lifecycle

A request supplies the exact list ID, stable item key, operation UUID and expected photo version. Possession of the list ID is the accepted shared-link access mechanism. Short/custom IDs can be guessed and anyone with the link can remove or replace photos. The server separately requires an explicit one-list allowlist, an enabled control and a finite deadline. A valid text item on another list is insufficient. The server does not enumerate lists/items or accept image-only items. Anyone who can add a valid text item under the existing text rules can then attach its photo; that follows the selected model.

The server rechecks the text item after processing and before commit, and before and after image reads. Expected versions plus deletion epochs fence asynchronous replacements. Reusing an operation UUID requires the same scope/version/input fingerprint and never grants a second physical upload. Historical replay returns its historical outcome without restoring an old current photo; the UI refreshes the current association after confirmation.

There is no distributed transaction across Firebase and Supabase. A text deletion immediately after the final existence check can temporarily leave a charged orphan association. Reads revalidate the item and will not intentionally expose an already-observed missing item. The deleting client's outbox sends `delete` even when the text item is now absent, but only an already-tracked photo item can be fenced; arbitrary nonexistent keys cannot create tombstones. An in-flight response or bytes already downloaded cannot be recalled. Lost clients/browser storage can still leave charged orphans: operational reconciliation is needed before a hosted beta.

Replacing a photo preserves the old current image until the new pair commits, then fences the old pair for cleanup. Removing a photo fences all earlier work; a later re-add uses a fresh operation and epoch. Deleting a text item permanently fences its stable key in the photo ledger. A successful physical PUT is marked stored; rejection, timeout or lost receipt leaves a **writing/unknown** grant. Unknown writers retain the full charge, occupy processing capacity, cannot be retried and are never refunded because of lease expiry or an empty lookup. Only settled, noncurrent objects may be deleted and verified absent before release. A never-written operation can be released after a fenced lease; a late encoder then cannot obtain a write grant.

Cleanup is user-triggered by replacement, remove, text deletion or retry/status of the same operation. There is **no silent photo TTL or scheduled deletion**. The seven-day proposal below is a service access window, not an object expiry. Deadline/kill-switch/cap exhaustion stops ordinary service; retained objects/history/unknown charges remain. A separately approved operator cleanup process is needed if users need removal after the service closes. Do not drop/truncate data or refund unknown writers to reopen capacity.

## Provisional finite envelope — review proposal, not finalized policy

| Limit | Proposed value and accounting |
| --- | --- |
| Selected lists | One exact server-side allowlisted list; currently empty |
| Service window | Seven days from later explicit enablement; exact UTC deadline currently null |
| Accounted storage | 10 MiB project-wide, including existing trial used/reserved bytes |
| Charged versions | 20, including pending/current/obsolete versions awaiting cleanup; replacement at this ceiling may be denied |
| Reservation | Full 416 KiB held per version until verified cleanup, even if actual outputs are smaller |
| Processing | Two pending or unknown-writer operations globally, including legacy pending work |
| Historical admissions / items | 100 each cumulatively; the existing 9 operations / 6 items consume capacity |
| Image delivery | 5 MiB and 100 Storage read attempts cumulatively; existing 2,359,296 bytes / 6 reads consume capacity |
| Request admission | 30 accepted requests per fixed minute and 500 over the beta; retries, status and failed text checks consume requests |
| Work | 512 KiB actual upload stream, ≤2048 chunks; 4-second body deadline, 8-second handler deadline, 6.5-second SDK fetch deadline, 30-second write authorization lease |
| Device retry intent | Up to 100 item markers; no image blobs or secrets |

The current client retrieves full and thumbnail together, so each image `get` charges two reads and 416 KiB **before either Storage read**, even on failure. Full-image lazy loading is a later optimization; this conservative implementation can reach the small delivery allowance quickly. Metadata/RPC/Storage protocol overhead and rejected Edge invocations are not covered by the image-byte counter. The separate **Free organization/project with no paid fallback/upgrade** is the spending boundary; these caps alone cannot promise zero provider overhead or resistance to deliberate denial of service. The fixed minute window permits a boundary burst. No per-IP identity or privacy-sensitive fingerprinting was introduced.
